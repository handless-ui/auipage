Guide 07换界面

流程只有一份，界面可以有很多种。这一章把上一章的 DOM 运行时换掉，看看哪些代码会动、哪些不会。

RuntimeDOMReact / Vue
01

会动与不会动

换 UI 框架时是否要改原因
AuiPage 的装配与调用不改它只认接口，不认渲染
三个 Adapter不改数据侧与界面无关
ChatContentRuntime重写append 里创建节点、返回更新函数
ThreadListRuntime重写侧边栏的列表与激活态
工具卡片重写它属于 ChatContentRuntime 的渲染范围

换句话说：状态机不动，只换“把状态画出来”的那一层。

02

原生 DOM 的两个约定

看起来只是 appendChild，其实有两个返回值的约定必须遵守，否则流式增量会整段重绘：

runtime/chatContent.js
const chatUI = new ChatContentRuntime({
    init: messages => {
        chatEl.innerHTML = "";
        messages.forEach(({ role, content }) =>
            content.forEach(part => renderPart(role, part))
        );
    },
    append: (role, part) => {
        const node = renderPart(role, part);

        // 约定一：文本类片段返回“更新函数”，后续增量只改这个节点
        if (part.type === "text" || part.type === "thinking" || part.type === "loading") {
            return text => {
                node.textContent += text;
                chatEl.scrollTop = chatEl.scrollHeight;
            };
        }

        // 约定二：tool-call 的 pending 片段返回“结束回调”，按 id 缓存到 success / error
        if (part.type === "tool-call") {
            return finalPart => updateCard(node, finalPart);
        }
    }
});
前端工具会回调两次：第一次带 render，由你在界面上做交互并返回界面结果； 第二次用界面结果做最终渲染。回传给模型的是 render 的返回值。
03

React / Vue：直接用现成实现

两个兄弟仓库就是这两个运行时的完整实现，装配方式与上一章完全一样，只是不再手写 DOM：

React

@auipage/react

ChatContent + ThreadList 两个组件， render-prop 把每个片段交给你，样式与结构完全自定义。

Vue

@auipage/vue

同结构、同接口，用作用域插槽渲染片段； 与 React 版共用同一份 AuiPage 流程。

自研

自己的组件库

继承两个 Runtime 基类，按约定实现钩子即可； 框架按 name 挂载，不要求特定生命周期。

如果只是固定用一个框架、一个页面，直接用这两个库比从零实现 Runtime 省事得多。

04

什么时候别换

运行时的意义是“同一套逻辑多处复用”。如果出现下面这些情况，抽象反而是负担：

  • 只有一个页面，且短期不会换框架——直接写组件更直接；
  • UI 需求非常定制（富文本编辑器、画布），Runtime 的钩子会成为约束；
  • 团队没有维护两套 Runtime 的成本，固定一个框架更省心。

框架给的是“可替换”，不是“必须替换”。
