Read 04agent：工具循环与两条回传通道

@auipage/agent 200 行，四个文件。它负责“让模型能动手”：一轮模型输出工具调用，执行，把结果塞回去，再来一轮。难点在工具可能跑在浏览器里。

200 行4 个文件maxSteps前端工具
01

Agent 的五个字段，和 maxSteps 的 0

{{src packages/agent/src/index.js#ctor}}

model 被包成 new Model(option.model)，所以外部传的是普通配置对象，不是 Model 实例。 这样在配置里写死 { model, apiKey, baseURL } 就能用，不必自己 import 一次。

maxSteps = option.maxSteps > 0 ? option.maxSteps : 0 这一行看起来啰嗦（等价于“不是正数就当 0”），但它防的是 undefined、 负数和 NaN：三者都会被归一成 0。0 在这里不是“一步都不许走”，而是“不限”—— 真正的解释发生在 runConversation 里（maxSteps > 0 ? maxSteps : Infinity）。 这种“0 表示无限”的约定在超时、timeout、前端工具超时里重复出现，是全库统一的口子。

signal 存在实例上而不是每次调用传参，因为一次对话里的多轮请求应该共享同一个取消信号： 用户按取消，正在等模型的那一轮要断，后面还没发的那几轮也不该再发。

02

system 提示词：原地改数组，还是新建数组

{{src packages/agent/src/index.js#system}}

这里是原地 unshift，会改掉调用方传进来的 messages。注释写得很明确：“原地修改，保持契约”。

为什么不返回一个新数组？因为上层（core 的 sendMessage）在多轮里会一直复用同一个 messages： 用户发第二条消息时，它希望看到的是“完整历史”，而不是每一轮都被重新包一次。原地改一次，历史里就多一条 system； 如果改成返回新数组而调用方忘了接住，下一轮就又没有 system 了。

代价是同一个数组不能跨 Agent 复用。所以有一道判重：首条已经是同内容的 system 就跳过。 没有这行判重，连续调两次 generate 会得到两条一样的 system，模型会当成两段不同指令，行为会飘。

判重条件里连 content 都参与比较：换了 system 提示词就会插入新的，旧的那条留在历史里。

这带来一个真实的坑：中途换人格时，旧人格还在上下文里。要彻底替换，得自己先 messages.shift() 掉旧 system，再调 generate。

03

runConversation：一轮对话其实是两条 assistant 消息

{{src packages/agent/src/runConversation.js#loop}}

maxSteps 的循环是 for (let step = 1; step <= maxSteps; step++)，没有 while (true)，也没有递归。 这样“超限”一定落在函数末尾那个 throw 上，而不是栈溢出——错误信息里还能带上真实的配置值。

一轮的结果被拆成最多两条消息：appendAssistantMessage 先推 { role:'assistant', content }， 再推 { role:'assistant', tool_calls }。这是 OpenAI 协议的要求——tool_calls 必须挂在一条 assistant 消息上， 而正文又得单独可读。两条消息的 tool_call_id 才对得上后面的 role:'tool'。

toolResults 用 await callFuns(...) 拿到与 tool_calls 等长的数组，然后用 forEach 按下标配对， 逐个 messages.push(toToolMessage(call, toolResults[i]))。顺序在这里被强制固定：模型发起的顺序 = 结果回填的顺序。 即使 callFuns 内部是并发执行、完成先后乱序，回填也一定按原序——否则历史里的 tool 消息和 tool_calls 就对不上号。

toToolMessage 里有一句 typeof value === "string" ? value : JSON.stringify(value) + ""。 加空串是为了处理 undefined（JSON.stringify(undefined) 返回 undefined 而不是字符串）， 工具没返回值时不能让 content 变成 undefined，否则整个 messages 序列化后会缺字段。

没有工具调用时直接 return result.content，只返回字符串、不返回整个 result。 想拿 tool_calls 的调用方拿不到——这是当前契约，需要 messages 自己去数组里翻。

04

callFuns：并发执行，失败当文本

{{src packages/agent/src/callFuns.js#map}}

并发来自 map + Promise.all：所有工具同时开始，等最慢的那个。 但这里有个容易被忽略的点：map 里的函数是同步返回 Promise 的，说明每个工具的执行都已经立即启动了—— 包括“工具不存在”“参数解析失败”这类根本不会执行的，也返回一个已 resolve 的 Promise 占位。用 Promise.resolve 而不是 null， 是因为后面 Promise.all 会把非 Promise 包一层，但占位分支若返回 null，toolResults[i] 就会变成 null 并在 toToolMessage 里变成 "null" 字符串。现在它能拿到一句人类可读的说明。

失败绝不让 Promise reject。三种失败（工具不存在、参数坏、执行抛错）全部转成字符串返回，交给模型“自己看怎么办”。 这是有意的：工具失败是对话的一部分，不是对话的终点。模型读到“参数解析失败:Unexpected token”能改参数重试； 如果整轮 reject，上层只会看到一次崩溃，用户还得从头再来。

两种 catch 都写了（同步 try/catch + .catch），因为工具可能是同步函数（throw 不会变成 rejected Promise）， 也可能是 async 函数。漏掉任何一个，同步抛错的工具就会把整轮对话打挂。

参数缺省按 {}：fn.arguments 是空串或缺失时直接给 {}，不调 JSON.parse。 否则空串会抛 Unexpected end of JSON input——无参工具全都会“失败”。

还有一点值得记：tool.execute(args) 被调用时不传第二参数。工具拿不到 signal、拿不到上下文， 所以工具内部想做取消必须自己从闭包里拿。这是设计上的缺口，不是忘了写。

05

createTool 的后端分支：同一个对象被改写两次

CreateTool(ms) 里的 ms 是一个“消息发送器”（在 core 侧由 MessageStream 提供）， create 把工具包装成一个恒定的形状：{ description, execute }——与 model 包需要的 description 恰好对齐。

{{src packages/agent/src/createTool.js#backend}}

两次 ms.send，一次 pending、一次 success/error。第二次发送用的是 initOption({ status, result }, toolInfo)，而 initOption 的实现是把 setOption 的键逐个写入第二个参数并返回它—— 也就是说，发出去的是同一个 toolInfo 对象，只是多了 status 和 result。 接收端能靠 id 把两条事件串起来，id 在第一次发送时就已经生成。

id = Date.now() + "_" + Math.random().toString(36).substring(2).toUpperCase()：时间戳保证排序，随机段保证同一毫秒内不撞。 它同时被用作 globalThis 的键（下一节），所以必须全局唯一，不能只用序号。

失败时 throw result 而不是 return：这一层先把“失败”事件发出去（用户能在界面上看到红色工具卡）， 再把错误抛给 callFuns，让后者转成给模型的文本。两层职责不重叠：事件给界面，异常给对话。

result = error; status = "error" 时把 error 直接塞进 result。所以前端拿到的 result 可能是一个 Error 实例——序列化过 SSE 之后它会变成 {}。这是当前版本的一个真实缺陷：错误详情到不了页面， 只能靠 status 区分。要修就得在这里做一次 String(error.message || error)。

06

前端工具：先建 Promise，再发事件

没有 execute 的工具被判定为“前端工具”：caller: "frontend"，实际执行发生在浏览器里。 服务端这一侧只做一件事——挂起等待，等页面把结果回传。

顺序是关键：new Promise 先建，ms.send 后发。注释写了原因：“避免页面同步回传时 _resolve 还不存在”。 如果先发事件，页面在同一 tick 里立刻回传（本地 ms 实现很可能就是同步派发）， globalThis[toolInfo.id] 还没挂上，回传就直接丢了，而这轮对话会永久卡住——没有报错、没有超时（如果没配 timeout），只是不动了。

回传通道是 globalThis[id] 一个全局函数，签名 function (result, status)。用全局而不是 ms 的某个注册接口， 是为了让页面侧（core 的 _handleChunk）能用最简单的方式回调，不需要再握一次引用。 代价是全局命名空间被占用，所以 done() 里一定 delete globalThis[toolInfo.id]—— 成功、失败、超时、发送抛错，四条路都会走到 done，否则就是内存泄漏（每个工具调用留一个闭包）。

settle 是“只兑现一次”的闸：回调里先 const current = settle; settle = null; 再调 resolve/reject。 先置空再调用，所以页面重复回传第二次时会看到 settle === null 直接 return，不会因为重复 resolve 或“成功后又报错”把状态弄乱。

timeout > 0 才起定时器，0 表示无限等。默认 0 是危险的：页面刷新、用户关标签，服务端就永远挂着。 所以文档示例里都建议显式传一个超时值。

ms.send(toolInfo) 外面还包了一层 try/catch：发送失败（比如流已经关了）就把 settle 清掉、done() 清理， 再 throw。不清的话，那个已经没人会调用的 globalThis[id] 会一直留着。

07

整条链路的边界条件

把四个文件连起来看，有几条“一定会遇到”的边界，写代码时最好先想一遍：

maxSteps 超限时抛出 "工具调用步骤超过 maxSteps 上限：" + 值。已经执行过的工具结果都留在了 messages 里， 所以上层可以选择继续调 generate 把对话接下去，而不是从头再来。core 的取消/继续就是靠这个前提成立的。

没有工具调用就结束：return result.content 可能是空串（模型只回了思考）。调用方不该把空串当失败。

工具返回非字符串会被 JSON.stringify，所以返回对象是安全的；返回 undefined 会变成 "undefined" 文本， 模型会读到这四个字母。工具里该 return "" 或 return { ok: true }，不要裸 return。

signal 只到模型请求：_this.signal 传进 completions，但不会传给工具。 取消一个正在跑的前端工具，只能靠工具自己的超时。
