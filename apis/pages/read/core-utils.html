Read 09纯函数：defineTool、generator 与两个转换器

四个没有外部依赖的文件，加起来 170 行。它们是整条链路里唯一可以单独测、不接任何端口的部分。

4 个文件约 170 行零依赖纯函数
01

defineTool：只换形状，不做校验

{{src packages/core/src/defineTool.js#shape}}

输入是写给开发者看的扁平结构 { name, description, parameters, execute, render }， 输出是两个消费者各自要的形状：description 被发给模型（OpenAI tools 格式）， execute 与 render 留在本地给 AuiPage 用。

它不校验名字唯一性，也不校验 parameters 是否合法 JSON Schema。重名的后果是 tools_execute[name] 里后一个覆盖前一个，静默覆盖、不报错。这是最该由它自己检查、却交给了调用方的一件事。

parameters 为 undefined 时，JSON.stringify 会把这个键整个丢掉。有些网关对缺失 parameters 的工具会直接拒绝， 所以无参工具应该显式写 { type: "object", properties: {} }。

它也没有把 execute 包一层 try/catch：异常兜底全部在 AuiPage 与 callFuns 里。 这样同一份 defineTool 产物可以同时给前端和服务端用，而两边的兜底策略本来就不同。

02

generator：把回调变成可 await 的迭代器

适配器里的写法是回调式的：拿到数据就 next(value)，结束就 done()，出错就 error(err)。 而 AuiPage 需要一个 for await 能用、还能 return() 的对象。generator.js 就是两者之间的转换器。

核心机制只一句话：生产者和消费者之间最多挂一个 Promise。

消费者快、生产者慢：queue 空且未结束，就 await new Promise(...) 挂起，把 { resolve, reject } 存进 pending。 生产者一进来看到 pending 存在，立刻 resolve 交值，不再入队。

生产者快、消费者慢：pending 为空，值进 queue；消费者下一轮先看 queue.length，有就 shift 直接产出。

为什么只留一个 pending：因为同一时刻只可能有一个消费者在等。for await 是串行的，不可能同时挂两个 await。 这个不变量让整段代码不需要锁，也不需要“待唤醒列表”。

03

五个变量：三个终态、一个缓冲、一个闸

变量含义谁写
queue已产出、未消费的值next() 回调
pending正在等值的消费者控制器，最多一个主循环与三个回调
ended生产者正常结束done() 回调
errored生产者异常；一旦设置，后续一切忽略error() 回调
cancelled消费者已退出；生产者再推也丢弃finally

ended 与 errored 是互斥终态：先到的那个生效，后面的回调直接 return。 三个回调第一行都是 if (errored || cancelled) return;，就是这个意思。

cancelled 的优先级更高：消费者 return()（_finalize 里那句 generator.return()）之后， 生产者即使还在跑，推的值也被丢掉——不能因为一个已经没人要的流把内存撑爆。

错误分发有两处：pending 存在时立刻 reject；不存在时只记 errored，由主循环在下一轮顶部 if (errored) throw errored; 抛出。两处都写，是因为错误可能发生在任何时刻。

04

finally 里的三件事

try/finally 的 finally 只在消费者主动退出时才有意义：cancelled = true（通知生产者闭嘴）、 queue.length = 0（释放已缓存值）、resolvePending({ done: true })（若有消费者挂着，让它以“结束”收场而不是永远等）。

为什么必须 resolvePending：退出就是那唯一的消费者，理论上不该还有人挂在 pending 上。 但留着 dangling 的 resolve 会一直持有闭包，所以这是内存层面的谨慎，不是逻辑必需。

还有一处不对称：done() 回调不管有没有 pending 都调 resolvePending（函数内部先判空，没挂起时什么都不做）， 但 ended 一定会置位。于是“生产者已结束、消费者还在排队”的情况，会在消费者把队列吃完后的 if (ended) return; 处收场。

toModelMessages：历史进模型的唯一闸门

{{src packages/core/src/tools/toModelMessages.js#flat}}

它是整个框架里唯一决定“什么能进模型上下文”的地方。三个过滤器值得逐个记。

① 只拼 text 片段（textOf）。thinking、loading、自定义类型全部不进上下文。 思考过程回灌既不省钱也不讨好——模型会重复思考一遍。

② 只保留已结束的工具调用：

{{src packages/core/src/tools/toModelMessages.js#calls}}

条件是 status === "success" || status === "error"。pending 的工具调用绝不能发出去： OpenAI 协议要求每个 tool_calls 后面必须跟一条 role: "tool" 的响应，缺了会直接 400。这行过滤就是那道保险。

③ 缺 id 时补一个稳定 id：call.id || ("call_" + (++seq))。seq 是本次转换内的自增， 所以同一份历史多次转换编号一致（顺序没变），但跨轮次不保证唯一。它只用于让 assistant 的 tool_calls[i].id 与后面 tool 消息的 tool_call_id 对上。

06

三个容易踩的细节

① content: text || void 0。一条 assistant 消息只有工具调用、没有正文时，content 被设成 undefined， JSON.stringify 会把整个键丢掉。有些服务商要求这个键必须存在且为 null，那就 400。当前实现选“丢掉”，兼容主流网关，但不兼容全部。

② arguments: JSON.stringify(call.args || {})。历史里的 args 是对象，模型要的是字符串。 无参工具固定序列化成 "{}" 而不是空串——空串会让某些网关把参数解析成 undefined。

③ payload = call.ui && call.ui.status ? call.ui.result : call.result。有界面交互时，发给模型的是用户选的值， 不是 execute 的返回值。这条规则在 AuiPage 里落库时就写好了，这里只是读出来用。

contentOf 的三段兜底也值得看一眼：字符串原样、Error 走 String(value)、其余先 JSON.stringify 失败再退回字符串。 Error 必须单独处理，因为 JSON.stringify(new Error("x")) 得到的是 {}。

07

toHistoryMessages：入库前把碎片焊回去

{{src packages/core/src/tools/toHistoryMessages.js#merge}}

流式过程中一段正文可能被拆成很多条 cacheMessages（类型切换、工具插入都会断开）。入库时不能一条条存， 否则下次加载历史会看到十几个气泡。这个函数负责把相邻且同角色的消息合并成一条，content 数组直接 push(...)。

它原地改写入参：value.messages = messages; return value;。传进来的对象会被换掉 messages 字段。 调用方 _finalize 正好要拿返回值继续用，所以看起来“没副作用”，但你手里原来的引用已经被改了。

只合并角色相同的相邻项，不跨越中间的其他角色。所以 assistant(text) 与 assistant(tool-call) 会合成一条， 而 assistant → tool → assistant 不会。

非合并项会拷贝：Object.assign({}, message, { content: message.content.slice() })。 但合并时是往原数组里 push——也就是说第一条被合并的消息，它的 content 数组被原地追加了。 想保证入参完全不被改，这里得再深一层拷贝。

这一页的四条规则，加上上一页 preType/preText 的合并带，是同一件事的两半：渲染时按批次流，入库时按语义合。
