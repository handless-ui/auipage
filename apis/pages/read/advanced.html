01

端到端时序：一句话走一圈

把用户按下发送到消息入库，压缩成十三步。每一步都能在源码里找到对应那段代码：

timeline
#  page                                   server
------------------------------------------------
1  sendMessage({role,content})   -------> ChatTransport.run
2                                         Agent.generate  (inject system)
3                                         Model.completions
4                                         fetch POST /chat/completions
5  next({type:"text"})           <------- SSE data
6  _handleChunk  merge band               
7  ChatContent.append                     
8  next({type:"tool-call"})      <------- SSE data
9  _handleToolCall -> execute             
10 response("tool-result")       -------> tool goes into messages
11                                        Model.completions (2nd round)
12 next({done:true})             <------- SSE [DONE]
13 _finalize -> toHistoryMessages -> append

三个交接点决定了整套架构：页面 ↔ 服务端之间是 generator（异步迭代器），服务端 ↔ 模型之间是 completions 的返回值， AuiPage ↔ 界面之间是 append 的返回值。三处都是“函数返回一个东西”，不是事件总线。 这是全套代码最一致的地方：每一层都能被 await，也都能被打断。

注意第 10–11 行的位置：tool-result 不是“回到原来那次请求继续跑”，而是新起一轮模型调用。 服务端那一轮在 Agent.generate 里其实已经结束了，页面回传的是新请求的输入。所以一次带工具的对话，至少两次 HTTP。

02

signal 怎么穿四层

取消之所以能真的停掉网络请求，是因为同一个 signal 从页面一路传到了 socket。链路一共四跳：

signal
AuiPage.cancel()
    |
    | _requestEnd("cancelled")
    ↓
task.controller.abort()          # AbortController
    ↓
adapter.run({ context: { signal } })
    ↓
Model.completions({ signal })
    ↓
fetch({ signal })
    ↓
adapter(requestOptions.signal)
    ↓
req.destroy()                    # Node: really close the socket

关键在 fetch 那一层做了“二次收敛”：外部传来的 signal 不直接给 adapter，而是先 addEventListener("abort") 转发到内部 controller，再把内部 signal 交给 adapter。于是 adapter 只需要认一个 signal，不必理解“是超时还是用户取消”。

另外两处不会断：stop() 也 abort（它和 cancel 共用 _requestEnd）， 但 signal 只到模型请求，不到工具。一个正在跑的前端工具拿不到取消信号，只能靠它自己的超时。

还有一条兜底：_requestEnd 在 busy 或 nextPending 时不起立即收尾，而是挂 _stopTimeout（默认 5000ms）。 这是给“适配器忽略 signal”准备的——signal 传了，对方不认，页面至少不会永远停在执行中。

03

片段状态机：合并带怎么迁移

_handleChunk 看起来只有两个分支，其实是一个由 preType 驱动的状态机。状态就是 task.preType：

preType收到什么发生什么
""（空）text / thinking / loading开带：preText = 首片，第一次渲染这条 assistant 消息
文本类同类型再来一片preText += text，streamFun 就地更新，不新建消息
文本类换了一种类型旧带落盘（_render 一次），再按上面的规则开新带
文本类流结束 done_finalize 把残留 preText 再落一次，然后清空
任意tool-call不入带，直接交给 _handleToolCall

四种正常情形对应四个行为：同类型续写只追加不渲染新消息；类型切换把旧带落盘、开新带； 流结束由 _finalize 补最后一片；tool-call 关掉旧带后直接交给工具。 真正没有兜底的是第五种——不属于白名单、也不是 tool-call 的类型，会被静默丢弃，这是当前实现里最容易埋新 bug 的地方。

入库时还有第二层合并（toHistoryMessages）：把相邻同角色的消息拼成一条。所以一次对话在内存里可能是 6 条， 入库后只剩 2 条。渲染按批次、入库按语义，这就是为什么两处逻辑不能合并。

单测用一套极简 DSL（describe / it / expect），全部是本地假适配器，不连网。跑法：node test/index.unit.js。

38 套件 / 148 用例，全绿。另有一套 *.spec.js 是联调脚本，只有设置 AUIPAGE_OLLAMA=1 才跑，默认跳过—— 它需要一个本地 ollama（默认 qwen3.5），所以不在 CI 里。

写新代码时，最该补的三类用例：① 片段的类型切换（合并带边界）；② 工具卡在没有 updater 时的落库；③ 取消发生在 nextPending 为真的那一瞬间。这三个位置目前都是“逻辑对、但很容易被改错”的地方。

走到这里，源码解读这一组就结束了。想动手改，建议顺序是：先改 toModelMessages（纯函数，风险最低）， 再改适配器（有测试兜底），最后才碰 AuiPage 的 pump 与工具通道。
