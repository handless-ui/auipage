01

先用六个函数把“出错”这件事关进笼子

文件开头到构造函数之前有六个小函数，它们不是工具函数，而是六个约束：让后面 600 行的主流程可以假设“外部调用不会炸我”。

1. mount：把适配器和运行时按名字挂上

{{src packages/core/src/AuiPage.js#mount}}

两个细节：instance.aui = aui 是反向引用，适配器里可以直接回调页面（比如工具需要读当前线程）；name.replace(suffix,"") 是命名约定—— 类名统一以 Adapter / Runtime 结尾，挂上来时把后缀剥掉，于是代码里写的是 this.adapter.ChatTransport、 this.runtime.ThreadList。这个名字是唯一契约，改类名不改后缀就会挂到错的位置。

没有 name 时回退到配置对象的 key（同样剥后缀），这样 { ChatTransport: MyImpl } 这种临时替身也能用。 if (!instance) continue 让 { ChatTransport: null } 变成“这个端口没接”，而不是崩在 instance.aui 那一行。

2. invoke：同步 / Promise / 未实现，三态归一

{{src packages/core/src/AuiPage.js#invoke}}

这个方法承载了“适配器可以是同步的，也可以是异步的”这个承诺。ret === undefined 被当作未实现而不是“完成”， 因为绝大多数可选端口（list、load、append）不实现时就是空函数。区分二者会让每个调用点都得写 !== undefined。 同步抛错直接 return（吞掉），Promise 拒绝也吞掉——适配器失败不该让页面白屏，最坏情况是列表空着。

3. callSafely / asUpdater：视图回调的两层兜底

{{src packages/core/src/AuiPage.js#safe}}

callSafely 的名字就是它的全部逻辑：异常吞掉、拒绝吞掉。它用在所有“交给外面”（streamFun、updater、事件 handler）的地方。 理由很实际：视图层一个 DOM 异常不该让整轮对话中断，也不该让取消流程卡住。

asUpdater 处理的是类型契约和实现的缝：ChatContent.append 的声明允许返回 void，但实现通常返回一个“更新这条消息”的函数。 允许不返回，就必须每次判断——所以这里把它归一成“函数或 null”，后面只判 null。

4. normalizeContent：字符串不许被逐字符渲染

{{src packages/core/src/AuiPage.js#content}}

用户消息的 content 允许传字符串（好写），但渲染接口只认片段数组。这里把字符串包成一个 text 片段。 如果直接 [...content]，一个中文字符串会被拆成 N 个片段，界面就会渲染成 N 条独立气泡——这是最容易踩的一脚。 空串返回 [] 而不是 [{text:""}]，避免渲染一个空气泡。

5. isCancelled 与那个 5000

{{src packages/core/src/AuiPage.js#cancelchk}}

isCancelled 只认 endRequest.status === "cancelled"，不认 stopped。这是全篇最重要的一条语义分界线： stop 要结果，cancel 不要结果。stop 之后工具结果继续落地，cancel 之后一切分片和工具结果直接丢弃。 DEFAULT_STOP_TIMEOUT = 5000 是给“适配器忽略 signal”的适配器准备的兜底——下页会看到它挂在哪个计时器上。

02

构造函数：为什么工具要拆成三份

{{src packages/core/src/AuiPage.js#ctor}}

options.tools 里的每个元素都是 defineTool 的产物：{ description, execute, render }。构造时被拆成三张表：

表内容谁在用
tools_description[{ description }]发给模型（ChatTransport.run 的 context.tools）
tools_executename → execute_handleToolCall 执行前端工具
tools_rendername → render_handleToolCall 需要界面拿结果时

不拆的话，每次查工具都要 find 一遍数组（O(n)），而且 description 与 execute 混在一个对象里， 很容易被误发给模型。拆表 = 物理隔离“能发给模型的”和“只能留在本地的”。

注意 tools_description 里只放 { description }，连 execute 的引用都不带——这样即使有人把它 JSON.stringify 发出去，也不会把函数序列化成一坨 undefined。

构造函数最后那个 invoke(this.adapter.ThreadList, "list", ...) 是启动即拉列表：同步适配器会在构造里就完成，异步适配器在 Promise 落定后完成。 这就是为什么文档里说“构造完界面可能还没列表”——它不保证已完成，只保证“问了”。

this._stopTimeout = options.stopTimeout > 0 ? options.stopTimeout : DEFAULT_STOP_TIMEOUT 沿用全库统一的“0 表示默认”的口子。

03

只有两个事件，而且必须复制数组

{{src packages/core/src/AuiPage.js#events}}

生命周期事件只有 task:start 和 task:end。没有 chunk、没有 message： 流式内容走 runtime.ChatContent.append 的返回函数，是推给视图而不是广播给订阅者。 两者分开是为了让“渲染”和“业务监听”互不打扰——订阅者不该为了拿增量而抢渲染顺序。

handlers.slice().forEach 有两个作用：复制防止回调里 off() 改数组导致跳过；每个 handler 单独 try/catch 防止一个监听器抛错让后面的监听器收不到事件。_emit 的 catch 是显式吞掉的，注释写明了。

on 允许订阅未知事件名（if (!this._events[event]) this._events[event] = []），所以第三方可以自己发明事件名， 只是永远不会被 _emit 触发——除非它自己也调 _emit。off 只删第一个匹配，重复注册三次就要删三次。

04

_render 里那本账：displayed

{{src packages/core/src/AuiPage.js#render}}

这个方法只做两件事，但第二件——task.displayed.push({ index, role, part })——是取消功能能用的前提。

原因是：runtime.ChatContent.append 一旦渲染，内容就进了视图层的状态，AuiPage 没有能力“撤回”。 所以要提前记下这一轮我到底往界面推了几条、分别是什么，取消时把 displayed 挂到 task:end 上， 由界面自己决定怎么撤销（删 DOM、回滚列表、还是只打个灰标）。

index 是本轮内的自增序号（displayed.length），不是全局消息下标。这样界面可以拿它判断“撤销这一轮的最后 N 条”。 role 与 part 原样存，是为了让界面不必回头去查自己刚才渲染了什么。

如果 runtime.ChatContent 没有 append（纯逻辑场景，比如服务端跑），这个方法直接 return， 连 displayed 都不记。所以别指望在没有视图的环境里靠 displayed 撤销什么东西。

05

这一页的边界：什么已经定了

到这里，AuiPage 已经具备的能力是：能挂端口、能存工具、能发事件、能渲染并记账。它还不具备的是：一轮对话怎么跑、分片怎么合、工具怎么回传。

两个值得先记住的约定，后面两页会反复用到：

端口名 = 类名去掉后缀。ChatTransportAdapter → adapter.ChatTransport；ThreadListRuntime → runtime.ThreadList。 自己写适配器时，类名必须以对应后缀结尾，否则挂上去的 key 会变成整个类名，运行时找不到。

外部一切调用都经过 invoke 或 callSafely。这意味着适配器里抛的错不会传到 sendMessage 的 Promise 上， 你在适配器里写的异常不会变成用户看到的报错。要报错就得走 generator 的 throw，或者 task:end.status = "error"。
