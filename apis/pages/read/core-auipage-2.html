Read 06AuiPage 中：sendMessage 与分片泵

一轮对话在 AuiPage 里不是 while 循环，而是一串 .then 串起来的泵。每一次 generator.next() 都是一个可以被打断的落定点。

148 行pumpendRequest合并带
01

入口：两道卫语句，两个字符串 reject

{{src packages/core/src/AuiPage.js#send}}

两个拒绝都是字符串而不是 Error：reject("当前正在执行中")、reject("消息格式不正确")。 所以 catch (e) 里 e.message 是 undefined，要 String(e) 才能拿到文案。这是当前版本的既有契约， 改它属于破坏性变更，暂时别动。

isExecuting 的复位点有三处：run() 同步抛错、generator 非法、以及最后的 _finalize。 前两处是“还没进执行期就失败”，必须手动复位，否则页面会永久卡在“执行中”，再也发不出第二条消息。

input 那行的三元判断值得注意：content 已经是数组时直接复用 message 对象，不是浅拷贝。 所以数组形态的消息会被 task.message 和 taskStart 事件共享同一个引用——监听器里改它，会改到任务自己的记录。

ChatTransport.run({ messages: [input], context: { history, tools, signal } })：只发当前这一条， 历史走 context.history。signal 是给适配器透传到底层 HTTP 的，这也是 cancel() 能真断请求的前提。

02

task 句柄：十九个字段，各管一段

这个对象是这一轮对话的全部上下文，被 pump、_handleChunk、_handleToolCall、_finalize 共享。

字段用途谁写
taskId自增序号，进事件与工具控制句柄构造
message / generator / controller输入、数据源、中断器构造
cacheMessages本轮要入库的消息数组全程
displayed已推给界面的条目（取消时撤销用）_render
preType / preText / streamFun当前“合并带”的类型、累积文本、更新函数_handleChunk
textTypes["loading","thinking","text"]，可流式的类型白名单构造
tool_callsid → updater，还没完结的工具卡_handleToolCall
ended / endRequest / endSignal终态、结束请求、唤醒信号构造 / _requestEnd
busy / nextPending“正在处理分片”“next 还没落定”pump
stopTimer取消的兜底计时器_requestEnd

busy 和 nextPending 是取消逻辑的核心：前者表示“正在处理分片/工具”，后者表示“next() 已调用但 Promise 未落定”。 只要有一个为真，_requestEnd 就不会立刻收尾——必须等手上这一块落完，否则这次工具的结果会从消息里丢掉。

03

pump：四个落定点，两条分岔

{{src packages/core/src/AuiPage.js#pump}}

pump() 每次只做一件事：调一次 generator.next()，然后把后续交给 .then。 之所以不用 while，是因为每次 next() 都可能 await 一个网络往返，用 while 就只能写 await， 而 await 会把整个函数变成异步，sendMessage 里那些同步卫语句就没法在“进执行期前”拦住了。

四个落定点，每个都必须检查 endRequest——顺序不能换：

① next() 同步返回前：try/catch 包住，同步抛错直接 _finalize("error", false, error)。

② next() 的 Promise 落定：先 nextPending = false，再判 endRequest → finishEnd()； 再判 ended；最后判 res.done → _finalize("complete", true)。

③ _handleChunk 完成：busy = false，同样先判 endRequest，然后 pump() 递归下一轮。

④ _handleChunk 拒绝：busy = false，endRequest 优先（丢弃分片异常），否则 _finalize("error")。

为什么 nextPending = true 写在 next() 之后：next() 可能同步返回一个已 resolve 的值， 这时 Promise.resolve(step).then 仍要等一个微任务。把 nextPending 置位在 next() 返回之后、.then 之前， 能保证整个这段空窗期里 _requestEnd 走“等待”分支而不是“立刻收尾”。

finishEnd 的第一行是 if (task.ended || !request) return;。!request 这个判断是为了让“分片完成时顺手调一次” 不会在没发起结束请求时误收尾——它是幂等入口，可以被四个落定点都调用一次。

04

_handleChunk：一条“合并带”

{{src packages/core/src/AuiPage.js#chunk}}

生成的片段有两种命运：能流的（loading / thinking / text）和不能流的（tool-call 等）。 能流的片段不会一条一条进 cacheMessages，而是先被合并——连续的同类文本会攒成一大段，最后只入一条消息。 这条合并带就是 preType + preText。

判据是 value.type != task.preType || !task.textTypes.includes(value.type)：类型变了，或者来的是特殊类型，就要关闭当前带。 关闭的动作只有两步：streamFun = undefined（旧流作废）、preText 非空则压进 cacheMessages。

然后分岔：非文本类型只处理 tool-call（交给 _handleToolCall），其它类型什么都不做—— 也就是说，适配器发来 {type:"plan"} 这类未知片段会被静默丢弃，既不渲染也不入库。这是当前的边界，扩展片段类型时必须同时改这里和白名单。

文本类型则开一条新带：记下 preText = text、preType，并调 _render 渲染第一个片段， 拿到的返回值存成 streamFun。注意传的是整个 value 对象（含 type 与 text）， 而不是只传 text——视图需要知道这是 thinking 还是正文。

同类型续写走 else：preText += text，然后 callSafely(streamFun, text) 把增量交给视图。 callSafely 在这里是必须的：streamFun 是视图返回的函数，抛错就会打断整个 pump。

一个容易忽略的后果：同一个类型连续出现时不会重复渲染，只追加文本。所以界面上看到的是“一条消息在长”， 而不是“每条 chunk 一个气泡”。这也是为什么 preText 要在类型切换时才落盘——它同时是渲染缓冲和历史缓冲。

05

streamFun 为什么会失效，以及为什么不用管

task.streamFun 是视图层返回的更新函数，它只对“刚刚那条消息”有效。一旦类型切换、开始一条新消息，旧函数就必须作废—— 否则增量会被写到上一条消息里。

作废的方式是直接置 undefined，而不是调用某种 unmount。这是故意的：视图层自己知道该消息何时结束（它拿到了下一片段）， 框架不去替它清理。AuiPage 只要保证不再往上一条消息写东西就够了。

副作用是：如果视图返回的 streamFun 依赖外部资源（比如定时器），框架不会帮你回收。 实现 ChatContentRuntime 时必须在“新片段替代旧片段”处自己收尾。

还有一处空窗：_handleChunk 开头 if (task.ended || task.endRequest) return。 结束请求一旦发起，后续所有片段被丢弃，包括正在路上的文本。这与 stop() 的语义（“结果要保留”）不冲突： stop 保留的是已经产出的内容，不是“还没到的”。
