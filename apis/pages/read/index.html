Read 01导读：怎么读这套源码

这一组文档不讲“怎么用”，只讲“为什么这么写”。五个包 src 一共 2010 行，AuiPage.js 一个文件占 692 行，所以它被拆成上、中、下三页单独讲。

01

五个包，一条从页面到模型的通路

依赖方向是单向的，没有环：core 和 agent 都只往上依赖，fetch 在最底下。所以单独装 @auipage/model 用、不装 core，是完全成立的。

包依赖一句话职责
fetch
273 行		宿主环境跨端请求、SSE 识别、超时与中断
model
277 行		fetch拼 chat/completions、解析流、归并 tool_calls
agent
200 行		model对话循环、工具编排、SSE 下发
core
1107 行		types消息与线程状态机、端口契约、工具定义
types
只有 .d.ts		无只放 .d.ts，运行时零依赖

两条链路在 model 这里才真正汇合：页面侧从来不碰 model，服务端侧也不碰 core。 它们之间唯一共享的东西是 @auipage/types 里的消息与事件结构，所以类型包出现在每个包的依赖表里，自己却什么实现都不带。

这里有一个刻意的控制反转：core 不直接发请求，它只认端口。sendMessage 把消息交给 ChatTransportAdapter，真实的网络、SSE 解析、鉴权全在适配器里。所以把文档站换成自家后端，或者拿去接一个第三方的 Agent 服务，都不用改 core 一行代码。

02

两条真实链路

后面十页反复出现的就是这两条路。先记住它们的“交接点”，读细节时就知道自己在哪一段。

页面侧：AuiPage.sendMessage() 建一个 task → 把消息交给 ChatTransportAdapter → 适配器把服务端 SSE 的每个事件（text / thinking / tool-call）翻译成片段 → _handleChunk 落成消息片段 → 前端工具在这里执行，结果经 response("tool-result") 回传 → task:end 收尾、可选入库。交接点是“片段”：适配器只要产得出片段，页面就能显示。

服务端：CreateTool 收到请求 → Agent.generate() 注入 system 提示 → runConversation 调 Model.completions() → 拿到 content 或 tool_calls → callFuns 执行工具 → 结果作为 tool 消息再进一轮 → 直到没有工具调用。 交接点是“ChatMessage 数组”：模型只认这一种入参。

page / server / model
page                      server
|                         |
| sendMessage             |
|------------------------>|  Agent.generate → model
|                         | model 流式返回
<-------------------------| text / thinking
<-------------------------| tool-call
| frontend tool runs      |
|------------------------>|  append tool message → model
|                         |
| task:end + save         |

左列是页面（AuiPage），中列是服务端（agent 的 CreateTool），右列是模型。 注意 tool-call 到 tool-result 之间那一行：前端工具是在页面里跑的，模型这一轮其实还挂着没结束。

03

术语表

这套源码的术语有点重名，先钉死含义，后面不再解释。

词准确含义（顺带标出它属于哪一层）
thread
core		会话线程，存标题与归档状态，由 ThreadListAdapter 持久化。不是“聊天记录”，记录在 message 里。
message
core		一条完整消息，含 role 与 parts；页面按 part 展示。它也不是模型入参，模型入参要经 toModelMessages。
part
core		消息片段，text / thinking / loading / tool-call 四类，都是增量，要自己拼。不是整段文本。
task
core		一轮发送的执行上下文：id、endSignal、items、status、signal。不是线程。
adapter
core 定义 / 业务实现		端口：ChatTransport、MessageHistory、ThreadList，方法可缺省。不是数据库层，只是方法契约。
runtime
core 定义 / 业务实现		页面上要渲染的 UI 能力：ThreadListRuntime、ChatContentRuntime。不是状态容器。
chunk
适配器 → core		适配器吐出的一批片段，即 _handleChunk 的入参。不是原始 SSE 行。
tool-result
core → 适配器		前端工具跑完后回传服务端的载荷 { id, status, result }。不是工具函数的返回值本身。
signal
core 透传到 model		AbortSignal，stop() 与 cancel() 都会 abort 它。它只管网络请求，不是 task 的“取消开关”。

三种阅读路线

十页都读是 4 万多字，多数人不需要。按你的目的挑一条：

你的目的读这几页大概能拿到

05

版本锚点与编写约定

这十页对应 v0.2.0。源码变了文档没跟上，就是我们这边的问题，欢迎开 issue。

为了让“事无巨细”不变成“代码朗读”，这一组有三条硬规矩：

  • 代码块不是手抄的。每段代码由构建期从 packages/ 里按 // #doc:标记 抽取，块头的 文件:起始行 由构建自动算出。源码一改，文档下次构建就跟着变，不存在“文档写的是老代码”。
  • 正文只按函数名引用。文里不会出现“第 137 行”这种写法，只写 sendMessage 的前半段、_handleToolCall 的后半段。行号会漂，函数名不会。
  • 每段必须回答五问。这段解决什么问题、为什么不用更简单的写法、输入输出与状态副作用是什么、出错时什么样、哪个测试锁住它。答不满五问的段落，我们就删掉。

另外两个看文档的小提示：每页右上（宽屏是右栏）都有页内目录，可以按章节跳；页末的「继续」是推荐顺序，不是唯一顺序。
