Read 08端口：Adapter 与 Runtime 的契约

core 里最“无聊”的六个文件，恰恰是整套框架能被替换的原因。它们全是同一个模板：声明默认值、把用户传的合并进来、挂上 name。

6 个文件114 行端口模式零依赖
01

一个模板，抄了五遍

ThreadListAdapter、MessageHistoryAdapter、ChatTransportAdapter、ThreadListRuntime、 ChatContentRuntime 这五个类，代码结构一模一样，差别只有“默认方法清单”和 name：

{{src packages/core/src/ChatTransportAdapter.js#ctor}}

把默认实现写成一个常量，再在构造里做一次“合并 + 拷贝”，好处是三个问题一次解决：

① 用户可以不实现任何方法。EmptyFunction 就是 () => void 0，一行。它让 AuiPage 里那些 this.adapter.ThreadList?.list(...) 的调用永远不会因为“方法不存在”抛 TypeError。

② 没传的键有兜底，传了的键覆盖。顺序是 initOption(options, {...DEFAUTL_OPTIONS})—— 把用户传的对象覆盖到默认值对象上。方向不能反，反过来会让默认实现盖掉用户的实现。

③ 只拷贝白名单里的键。for (let key in DEFAUTL_OPTIONS) 遍历的是默认值对象的键，不是用户对象的键。 这意味着用户多传的属性会被静默丢弃。想在适配器上挂自定义方法，不能通过配置对象传，只能加在原型上或者用闭包。

02

那个展开运算符不是装饰

{{src packages/core/src/ChatTransportAdapter.js#merge}}

{ ...DEFAUTL_OPTIONS } 必须存在。因为 initOption(setOption, defaultOption) 的实现是 把 setOption 的每个键写进 defaultOption 并返回它——它是原地改写第二个参数。

如果直接写 initOption(options, DEFAUTL_OPTIONS)，模块级常量就被第一个实例改掉了： 第一个页面传了 run: A，第二个页面即使不传，也会拿到 run: A。 这是“共享可变默认值”的经典坑，展开一次就把每个实例隔离开。

let value = ... 之后还要 for (let key in DEFAUTL_OPTIONS) this[key] = value[key]，而不是直接 this.run = value.run。 这样新增一个默认方法只改常量，构造函数不用动。

注意 DEFAUTL_OPTIONS 的拼写：源码里少了一个 I（正确是 DEFAULT）。你在文件里搜 DEFAULT_OPTIONS 是搜不到的，这是历史遗留，不影响运行。

03

name 字段：唯一的“接口声明”

每个类都硬编码了一行 this.name = "ChatTransportAdapter"。它没有任何类型检查作用，只被 mount 用来剥后缀：

name.replace("Adapter","") → "ChatTransport"，于是页面里写 this.adapter.ChatTransport。 类名、name 字段、mount 的后缀三者必须一致。改名时漏一处，就是这个端口“接了但调不到”——而且不会报错，因为默认实现本来就是空函数。

这也解释了为什么 AuiPage 构造函数里调用的是 this.adapter.ThreadList?.list(...)，而不是 this.adapter.ThreadListAdapter。 后缀是给 mount 剥的，不是给业务代码用的。

05

MessageStream：给工具一个“往页面推”的口子

{{src packages/core/src/MessageStream.js#ctor}}

它只有两个字段，没有 name，也不走 mount。因为它不是端口，是一个通道：

send 被 createTool 用来推 tool-call 事件（pending 与 success/error 两次）， end 用来在流结束时收尾。方向是单向的：服务端 → 页面。

反方向（页面 → 服务端）不走这里，走的是 ChatTransportAdapter.response("tool-result", ...)。 两条通道分开，是因为它们的生命周期不同：MessageStream 跟着一次 HTTP 流，response 是独立的一次请求。

send || EmptyFunction 这个兜底很重要：没有 ms 时（比如在纯逻辑测试里造一个 CreateTool）， 工具调用会“静默发不出去”，但不会抛错——这让你可以单独测 execute 而不启动服务端。

06

为什么不写接口声明

这五个类没有 abstract、没有 interface、也没有 throw new Error("not implemented")。 全部用空函数兜底，是有意的取舍：

① 零依赖且跨端：core 要能在浏览器里跑，不能依赖 Node 的 EventEmitter，也不引入类型库。

② 允许“部分实现”：只想做一个只读列表？只实现 list 就行，其它方法空着，页面能跑。如果强制实现，最小用例就得多写十个空方法。

③ 契约靠文档和类型文件：@auipage/types 里的 .d.ts 才是真正的契约声明。运行时故意不校验—— 宁可让开发者少写代码，也不要为了报错而增加启动成本。

代价也很明显：实现错了不会在构造期发现。run 返回了非迭代器，要到 sendMessage 里那句 typeof generator.next !== "function" 才报 "ChatTransport.run() 返回空值"。排查这类问题时， 先怀疑 name，再怀疑返回形状。
