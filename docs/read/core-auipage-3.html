Read 07AuiPage 下：工具通道与收尾

工具调用在 AuiPage 里是两段式的：pending 先挂卡，success / error 再回填。中间那一段，可能是在等用户点按钮。

2 个频道Promise.racestop ≠ cancel_finalize

01

pending：先挂视图，再决定谁执行

packages/core/src/AuiPage.js:428
AuiPage.prototype._handleToolCall = async function (task, call) {

    // 工具开始调用（前端工具 + 后端工具）
    if (call.status === "pending") {
        const updater = asUpdater(this._render(task, "assistant", call));
        if (updater) task.tool_calls[call.id] = updater;

        // 后端工具由 ChatTransport 自己执行，这里只挂视图
        if (call.caller !== "frontend") return;

        // 前端工具需要自己执行；第二个参数是任务控制句柄，工具里可直接 stop / cancel
        const execute = this.tools_execute[call.name];
        const control = this._toolControl(task, call);
        let result, status;

        if (typeof execute === "function") {
            try {
                result = await execute(call.args, control);
                status = "success";
            } catch (error) {
                result = error;
                status = "error";
            }
        } else {
            result = new Error("未注册的工具：" + call.name);
            status = "error";
        }

        // 工具执行期间被取消：结果丢弃；被 stop 则继续把这次调用的结果落地
        if (task.ended || isCancelled(task)) return;

        const render = this.tools_render[call.name];

pending 分片里做的第一件事是 渲染，而不是执行。渲染返回的更新函数被 asUpdater 归一后存进 task.tool_calls[call.id]——这张表是“还没完结的工具卡”登记处，后面所有回填都要靠它找到卡片。

然后立刻分流：if (call.caller !== "frontend") return;。后端工具的 execute 由 ChatTransport 在服务端跑， 页面这一侧只负责显示，不该重复执行一次。前端工具（caller === "frontend"）才继续往下走。

这个分岔点也解释了为什么会有两条回传通道：服务端的 createTool 直接 await execute，页面的工具则在 _handleToolCall 里 await execute，然后用 ChatTransport.response("tool-result") 把结果送回去。

02

执行前端工具：失败也要变成“结果”

执行那段只有十几行，但把“工具是人写的”这件事考虑进去了：

execute 通过 tools_execute[call.name] 查表；查不到就造一个 new Error("未注册的工具：" + call.name)， 状态记 error。工具抛错同样落成 result = error、status = "error"。

异常不外抛：如果这里 throw，_handleChunk 会 reject，pump 会走 _finalize("error")， 整轮对话直接失败。而“工具跑挂了”在语义上只是一次调用失败，应该让模型看到错误信息并决定怎么办——所以它被当成结果。

第二个参数 control 来自 _toolControl：{ taskId, toolCallId, stop(), cancel() }。 这是工具唯一能主动结束对话的入口，它绑定了自己所属的 task，所以不会误杀下一轮。

执行完立刻有一次取消检查：if (task.ended || isCancelled(task)) return;。 cancel 之后结果丢弃，stop 之后继续落地——这两句就是上一页那条语义分界线的落点。

03

要界面拿结果：一场 race

packages/core/src/AuiPage.js:464
if (typeof render === "function" && updater) {
    const pending = Promise.resolve(updater(Object.assign({}, call, {
        result: result,
        status: status,
        render: render,
        taskId: control.taskId,
        stop: control.stop,
        cancel: control.cancel

    // 界面还挂着等交互时被结束：放弃等待，按 execute 的结果收尾
    const outcome = await Promise.race([
        pending.then(function (value) {
            return { value: value };
        }, function (error) {
            return { error: error };
        }),
        task.endRequest
            ? Promise.resolve({ ended: true })
            : task.endSignal.promise.then(function () { return { ended: true }; })
    ]);

    if (task.ended || isCancelled(task)) return;

    if (outcome.ended) {
        callSafely(updater, Object.assign({}, call, { result: result, status: status }));
        delete task.tool_calls[call.id];

        task.cacheMessages.push({
            role: "assistant",
            content: [{
                type: "tool-call",
                name: call.name,
                args: call.args,
                result,
                status
            }]
        });

        return;
    }

    let result_ui = outcome.error !== void 0 ? outcome.error : outcome.value;
    let status_ui = outcome.error !== void 0 ? "error" : "success";

    callSafely(updater, Object.assign({}, call, { result: result_ui, status: status_ui }));
    delete task.tool_calls[call.id];

    task.cacheMessages.push({
        role: "assistant",
        content: [{
            type: "tool-call",
            name: call.name,
            args: call.args,
            result,
            status,
            ui: { status: status_ui, result: result_ui }
        }]
    });

    invoke(this.adapter.ChatTransport, "response", null, ["tool-result", {
        id: call.id,
        status: status_ui,
        result: result_ui
    }]);
}

如果工具还提供了 render，说明它不只是显示，还要从界面里取一个值（比如“选一个文件”“确认删除”）。 于是 updater 被调用，参数是整张卡的数据 + render 函数 + control； updater 的返回值被 Promise.resolve 包起来，界面返回 Promise 就是在等用户，返回普通值就是立刻完成。

等待期间必须能被打断，所以有这场 Promise.race：一边是界面的 Promise，另一边是 endSignal.promise （stop() / cancel() 时 resolve）。谁先落定，谁决定这次工具怎么收场。

race 的第二个分支是先判 task.endRequest 再等信号的：如果结束请求已经存在，立即结束，不用等到信号被 resolve。 这是为了处理“请求发起时，工具刚好在挂卡之前”的时序。

outcome.ended 分支：界面还没回话就被结束，这时拿不到 UI 结果，于是退回 execute 的结果收尾，卡片按 result/status 定格，消息入 cacheMessages，但不调用 ChatTransport.response—— 因为对话已经结束了，再回传一个 tool-result 会让服务端多跑一轮。

正常分支：outcome.error 与 outcome.value 决定 status_ui，卡片用 UI 结果定格， 消息里同时记两套结果：result / status（execute 的）与 ui: { status, result }（界面的）。 为什么要两套：模型需要的是 execute 的结果，界面需要的是用户选的值，两者可能不一样（比如 execute 返回“拿到参数了”，用户实际选了另一个文件）。

最后 invoke(this.adapter.ChatTransport, "response", null, ["tool-result", { id, status, result }])： 发回去的是 UI 结果，因为对模型来说“用户选了什么”才是它要的答案。invoke 吞掉异常，所以回传失败不会影响界面。

else 分支处理两种情况：工具没有 render，或者视图层没返回 updater（比如纯逻辑测试环境）。 这时只做“定格卡片 + 落消息 + 回传”。

注意这里的 if (updater)：没有 updater 也要落消息。视图缺失不该让历史缺一条工具结果， 否则下一轮模型看到的上下文里，“它调用过工具”这件事就消失了。

两个分支的 ChatTransport.response 参数形状略有不同（一个 {id,status,result} 顺序无关，一个多一层）， 但字段名一致。适配器实现只要认这三个字段。

后端工具的回填：靠 id 找卡

packages/core/src/AuiPage.js:564

                status: call.status
            }]
        });
    }
}

后端工具的结果是服务端推回来的 success / error 分片。这里不做执行，只做回填： 从 task.tool_calls[call.id] 拿到卡片更新函数，调一次，删掉登记，再落一条消息。

外层 if (task.tool_calls[call.id]) 是全部条件：如果这张卡不存在（比如 pending 分片丢了、或者取消时已经 delete）， 这段什么都不做——结果分片被静默丢弃，消息也不会入库。这是当前版本的一个真实缺口：网络抖动导致 pending 丢失时， 历史里就会少一条工具调用。id 是唯一线索，所以它必须是全局唯一的（createTool 那个时间戳 + 随机段就是为此）。

call.result 直接落进消息，不做任何序列化处理。所以后端工具返回 undefined 时， 这条消息的 content[0].result 会是 undefined，JSON.stringify 之后这个键直接消失。

06

stop 与 cancel：同一套机制，两种口径

packages/core/src/AuiPage.js:310
AuiPage.prototype._requestEnd = function (status, by, task) {
    task = task || this._currentTask;
    if (!task || task.ended) return false;
    if (task.endRequest) return true;

    task.endRequest = { status: status, by: by };

    // 中断底层请求；适配器把 context.signal 透传下去即可立即停止
    callSafely(function () {
        if (task.controller) task.controller.abort();
    });

    // 唤醒可能卡在界面交互里的流程
    callSafely(task.endSignal.resolve);

    if (task.busy || task.nextPending) {
        // 等着当前分片落定；兜底超时防止适配器忽略 signal 时页面停在执行中
        const _this = this;
        task.stopTimer = setTimeout(function () {
            _this._finalize(status, true, null, by, task);
        }, this._stopTimeout);
        if (task.stopTimer && typeof task.stopTimer.unref === "function") task.stopTimer.unref();

        return true;
    }

    this._finalize(status, true, null, by, task);
    return true;
};

/**
 * 取消当前任务：中断底层请求，已产出的部分照常入库并标记 cancelled，
 * task:end 附带 displayed，界面可自行撤销。
 *
 * @returns {boolean} 当时是否有正在执行的任务
 */
AuiPage.prototype.cancel = function () {
    return this._requestEnd("cancelled", "user");
};

/**
 * 交给工具的任务控制句柄：execute / render 里直接调用 stop() 或 cancel()。
 *
 * @param {object} task 任务句柄
 * @param {object} call 工具调用分片
 */
AuiPage.prototype._toolControl = function (task, call) {
    const _this = this;
    return {
        taskId: task.taskId,
        toolCallId: call.id,
        stop: function () { return _this._requestEnd("stopped", "tool", task); },
        cancel: function () { return _this._requestEnd("cancelled", "tool", task); }
    };
};

_requestEnd 只做四件事：记下请求（endRequest = { status, by }）、abort() 底层请求、 resolve endSignal（唤醒卡在界面等待的 race）、然后决定立刻收尾还是等一拍。

“等一拍”的条件是 task.busy || task.nextPending：有分片或工具正在处理时，abort() 不能让它们手里的结果凭空消失。 于是挂一个 setTimeout(_stopTimeout)，超时才强制 _finalize。unref() 那一行是给 Node 用的： 这个计时器不该阻止进程退出。

stop() = _requestEnd("stopped","user")；cancel() = _requestEnd("cancelled","user")。 差别只出现在收尾口径上：stop 当成功收尾（内容保留、入库标 stopped、Promise resolve）； cancel 中断请求、入库标 cancelled、Promise reject("已取消")，并把 displayed 挂到 task:end 上供界面撤销。

为什么 cancel 也入库：用户取消不等于“这段对话没发生过”。保留半截内容 + 一个 cancelled 标记， 刷新后还能看到一个“已取消”的轮次；直接丢弃会让历史出现空洞。

重复调用是安全的：if (task.endRequest) return true;，第二次直接返回“已经有任务在结束中”，不重复 abort、不重复计时。

07

_finalize：四步，且每一步都能失败

packages/core/src/AuiPage.js:595
AuiPage.prototype._finalize = async function (status, isHistory, err, by, taskArg) {
    let task = taskArg || this._currentTask;
    if (!task || task.ended) return;
    task.ended = true;

    // 清理兜底计时器，并释放还在等结束信号的流程
    if (task.stopTimer && typeof clearTimeout === "function") clearTimeout(task.stopTimer);
    task.stopTimer = null;
    callSafely(task.endSignal.resolve);

    // 1. 残留文本归并到 cacheMessages
    if (task.preText) {
        task.cacheMessages.push({
            role: "assistant",
            content: [{ type: task.preType, text: task.preText }]
        });
        task.preText = "";
        task.preType = "";
    }

    // 2. 让生成器停止继续产出（此时 next() 已 settle，可安全调用）
    if (typeof task.generator.return === "function") {
        callSafely(function () { return task.generator.return(); });
    }

第 0 步是幂等闸：if (!task || task.ended) return; 然后立刻 task.ended = true。 因为 _finalize 可能被四个地方同时叫到（pump 的两条分岔、_requestEnd 的两条路径、兜底计时器）， 先置位再干活，后面无论怎么重入都只会执行一次。

第 1 步：残留文本归并。把 preText 收尾成一条 assistant 消息，否则最后一段流式文本会丢。 这也解释了为什么 preText 要留到类型切换才落盘——流结束时它一定还在，就靠这里兜住。

第 2 步：generator.return()。此时 next() 已 settle，调用 return 是安全的， 它会让适配器里的 try/finally 跑到，从而关闭 HTTP 流、清理计时器。typeof === "function" 的判空是因为 适配器可能返回一个只有 next 的极简迭代器。

packages/core/src/AuiPage.js:622
    // 3. 入库；失败降级为 error，避免前端误以为消息已保存
    let failure = status === "error" ? err : null;

    if (isHistory && !failure) {
        try {
            let historyMessages = toHistoryMessages({ messages: task.cacheMessages });

            // 主动结束与取消也入库，只打标记；存或丢由 MessageHistory.append 自己决定
            if (status === "stopped" || status === "cancelled") historyMessages.status = status;

                if (!newThread) throw new Error("新建会话失败");

                await Promise.resolve(this.runtime.ThreadList?.append(newThread));
                this.activeThread(newThread.threadId, true);
            }

            this.currentMessages.push(historyMessages);
            await this.adapter.MessageHistory?.append?.(this.currentThreadId, historyMessages);
        } catch (e) {
            failure = e;
        }
    }

    // 4. 复位、emit task:end、释放 Promise
    if (this._currentTask === task) {
        this.isExecuting = false;
        this._currentTask = null;
    }

    const finalStatus = failure ? "error" : status;

    const payload = {
        taskId: task.taskId,
        threadId: this.currentThreadId,
        message: task.message,
        status: finalStatus
    };

    // 主动结束 / 取消时说明是谁发起的；取消另附已显示条目，界面据此决定是否撤销
    if (finalStatus === "stopped" || finalStatus === "cancelled") payload.by = by || "user";
    if (finalStatus === "cancelled") payload.displayed = task.displayed;

    this._emit("task:end", payload);

    if (finalStatus === "error") task.reject(failure || new Error("任务执行失败"));
    else if (finalStatus === "cancelled") task.reject("已取消");
    else task.resolve();
};

第 3 步：入库。三种情况会走：complete、stopped、cancelled（即 isHistory === true）， error 不走。status 被塞进 historyMessages 上作为一个字段—— 存不存由 MessageHistory.append 自己决定，框架只负责把标记递过去。

没有当前线程时先建一个：ThreadList.new(historyMessages) → ThreadList.append → activeThread(threadId, true)。 第三个 true 是 __noLoad__：刚建的空线程不需要回头加载历史，省一次往返。

入库失败会降级成 error：catch (e) { failure = e; }，最后 finalStatus = failure ? "error" : status。 这是为了不让前端以为“消息已保存”。代价是：本来成功的这轮，会因为写库失败而让 sendMessage reject。

第 4 步：复位与释放。if (this._currentTask === task) 才复位 isExecuting——这个身份判断很关键： 兜底计时器可能在下一次 sendMessage 之后才触发，如果无条件复位，就会把新任务的状态给清了。

最后按 finalStatus 三选一：error → reject(failure)；cancelled → reject("已取消")；其余 → resolve()。 resolve() 不带值，调用方拿不到内容，要内容得看视图或 currentMessages。

08

线程操作：四个薄壳，一个开关

packages/core/src/AuiPage.js:676
AuiPage.prototype.activeThread = function (threadId, __noLoad__) {
    if (this.currentThreadId === threadId) return;

    // 已经有执行的，不允许切换
    if (this.isExecuting && !__noLoad__) return;

    this.currentThreadId = threadId;
    this.runtime.ThreadList?.active(threadId);

    if (threadId === void 0) {
        this.currentMessages = [];
        this.runtime.ChatContent?.init([]);
        return;
    }

    if (__noLoad__) return;

    // 加载历史消息
    invoke(this.adapter.MessageHistory, "load", (messages) => {
        this.currentMessages = messages;

        let plainMessages = [];
        messages.forEach(item => {
            plainMessages.push(...item.messages);
        });
        this.runtime.ChatContent?.init(plainMessages);
    }, [threadId]);
};

activeThread 有两个守卫：相同 id 直接返回（避免重复加载）和执行中不许切换（isExecuting && !__noLoad__）。 第二个守卫是为了不让“正在生成的对话”被切走——那会让 _finalize 把消息写进另一个线程。

__noLoad__ 是内部参数（双下划线命名就是提示“别从外部传”）：跳过 MessageHistory.load。 只有 _finalize 新建线程时用得到它。

加载历史时有一个拍平动作：messages.forEach(item => plainMessages.push(...item.messages))—— 存的是“按轮分组”的结构，界面要的是“一条条消息”。这个转换不做去重也不做排序，完全依赖适配器返回的顺序。

        this.runtime.ThreadList?.delete(threadId);

        if (threadId === this.currentThreadId) this.newThread();
    }, [threadId]);

AuiPage.prototype.archiveThread = function (threadId) {
    invoke(this.adapter.ThreadList, "archive", () => {
        this.runtime.ThreadList?.archive(threadId);

        if (threadId === this.currentThreadId) this.newThread();
    }, [threadId]);
};

AuiPage.prototype.unarchiveThread = function (threadId) {
    invoke(this.adapter.ThreadList, "unarchive", () => {
        this.runtime.ThreadList?.unarchive(threadId);
    }, [threadId]);

删除和归档都遵循同一个模式：先让适配器做，成功后更新视图，如果删的是当前线程就 newThread()。 这是“适配器是唯一真相”的体现——视图永远等适配器确认。

newThread() 就是 activeThread(undefined)：清空 currentMessages、清空视图、不发任何请求。
