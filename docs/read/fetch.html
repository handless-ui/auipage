01

为什么既要 Promise 又要事件

原生 fetch 的做法是：fetch() 给你一个 Response，你自己 res.body.getReader() 读流。 这个模型在浏览器里没问题，但到 Node 端要换一套 http.request 的事件写法，两边的“读流”长得完全不一样。 createFetch 的办法是把差异压进 adapter，外面只留一套统一壳：

packages/fetch/src/fetch.js:11
return function fetch(options) {
  // 必须返回 Promise<response>，让调用方能 .then(res => res.on(...))
  return new Promise((resolve, reject) => {
    if (!options || !options.url) {
      reject(new Error('fetch: options.url is required'));
      return;
    }

    // 请求体是普通对象时自动序列化，避免 Node 端 req.write(object) 抛 TypeError
    if (isPlainBody(options.body)) {
      options = Object.assign({}, options, { body: JSON.stringify(options.body) });
    }

    const response = new Response();
    const controller = typeof AbortController === 'function' ? new AbortController() : null;
    let timer = null;
    let failed = false;

    response._cancel = () => { if (controller) controller.abort(); };

    // adapter 调用前先把 response 交出去，确保 .then(res => ...) 里能立刻 on(...) 注册监听
    // 用 queueMicrotask 推后一拍，避免同步 resolve 后用户立刻注册的监听错过首个 data
    queueMicrotask(() => resolve(response));

三个决定值得逐个说。

返回 Promise 而不是直接返回对象：因为 options.url 缺失这种参数错误必须能被 catch 到。如果直接返回 Response，这类错误只能从 error 事件里取，调用方写 try/catch 就抓不到。

queueMicrotask(() => resolve(response)) 推后一拍：这是全文件最容易看漏的一行。调用方拿到 response 是在 .then 回调里， 而 adapter 的第一块数据最早也要等一个真实的 I/O 回来。先把 resolve 排进微任务队列，能保证 .then 里的 on() 一定先于第一个 data 执行——否则首个 chunk 会在没人监听时被丢掉。 它同时也是“resolve 一定在 adapter 调用之后入队、却先执行”的原因：adapter 内部至少有一次 await。

普通对象请求体自动 JSON.stringify：只判 [object Object]。FormData、Blob、ArrayBuffer 一律原样透传， 否则上传二进制会被字符串化毁掉。Node 端 req.write(object) 会直接抛 TypeError，所以这一步在 Node 上是必需的，不只是顺手。

还有一行不起眼、但决定了取消能不能用：response._cancel = () => controller.abort()。取消能力挂在 Response 上， 而不是通过参数传进去——因为调用方通常在拿到 response 之后才知道要不要取消。

02

hooks 的四个口子，和 SSE 是怎么被认出来的

adapter 只被允许回调四件事：拿到了响应头、来了一块数据、结束了、出错了。所有状态改写都集中在 onResponse 里：

packages/fetch/src/fetch.js:44
const hooks = {
  onResponse(meta) {
    if (meta && typeof meta.status === 'number') {
      response.status = meta.status;
      response.ok = meta.status >= 200 && meta.status < 300;
    }
    if (meta && meta.headers) {
      response.headers = meta.headers;

      // 自动检测 SSE：浏览器 Headers 对象用 get()，Node 的 plain object 用 []
      const contentType =
        (typeof meta.headers.get === 'function' && meta.headers.get('content-type')) ||
        meta.headers['content-type'] ||
        '';
      if (contentType.includes('text/event-stream')) {
        response._sseMode = true;
      }
    }

    // 非 2xx 单独通知：不占用 error 事件、不锁 _done，错误体照常投递
    if (response.status >= 400) {
      response.emit('http-error', { status: response.status, headers: response.headers });
    }
  },
  onData(chunk) {
    response._push('data', chunk);
  },
  onEnd() {
    clearTimer();
    response._push('end');
  },
  onError(err) {
    if (failed) return;
    failed = true;
    clearTimer();
    // 错误同时通过 error 事件 和 catch 暴露，避免遗漏
    response._push('error', err);
    reject(err);
  }
};

status / ok 在这里落地，adapter 不再关心语义，只报数字。

SSE 判定写了两种取值方式：浏览器给的是 Headers 对象（要 .get()），Node 给的是普通对象（要 []）。 这一行 (typeof headers.get === 'function' && headers.get('content-type')) || headers['content-type'] 就是为跨端准备的， 和 Response.header() 里那套判断是同一个思路，只是这里不方便多调一次方法。

http-error 是一个独立事件，这是有意的设计：4xx/5xx 既不算“网络错误”，也不能算“成功”。 它不触发 error、也不置 _done，所以错误响应体还会照常从 data 流下来—— 上层的 completions 正是靠这一点，把 {"error":{"message":...}} 读出来拼进错误信息。

反过来，onError 里同时做了两件事：_push('error') 和 reject(err)。 事件是给“已经在听”的人，reject 是给“还在 await”的人，两条路都要通，否则总有一类调用方会永远挂住。 failed 这个布尔量只干一件事：防止 abort 之后的又一次 error 重复 reject。

03

超时和取消，最后都变成同一个 abort

packages/fetch/src/fetch.js:87
const abortWith = (err) => {
  if (controller) controller.abort();
  hooks.onError(err);
};

// 超时：到点先中断底层请求，再走统一错误通道
if (options.timeout > 0) {
  timer = setTimeout(() => {
    timer = null;
    abortWith(new Error('fetch: 请求超时（' + options.timeout + 'ms）'));
  }, options.timeout);
}

// 外部 signal
if (options.signal) {
  if (options.signal.aborted) {
    abortWith(new Error('fetch: 请求已取消'));
    return;
  }
  options.signal.addEventListener('abort', () => {
    abortWith(new Error('fetch: 请求已取消'));
  });
}

// 把内部 controller 的 signal 交给 adapter，adapter 可据此中断底层请求
const requestOptions = controller ? Object.assign({}, options, { signal: controller.signal }) : options;

let ret;
try {
  ret = adapter(requestOptions, hooks);
} catch (err) {
  hooks.onError(err);
  return;
}
// adapter 允许返回 Promise，失败也要走同一条错误通道
if (ret && typeof ret.then === 'function') ret.then(null, hooks.onError);

这段里有两层 signal：外面传进来的 options.signal，和内部 new AbortController() 的 controller.signal。 真正交给 adapter 的只有内部那个（Object.assign({}, options, { signal: controller.signal })）。 外部 signal 做的事只有一件：addEventListener('abort', ...) 转发成 controller.abort()。

这么绕一圈的原因是“超时”和“手动取消”在语义上是两件事，但对底层请求来说是同一件事：中断 I/O。 把两条来源都汇到 abortWith，adapter 就只需要认一个 signal，不必区分是自己超时了还是被用户按了取消。 代价是：错误文案在这里就定了（请求超时 / 请求已取消），上层想区分只能靠 message 字符串，没有 code 字段。这是当前版本的取舍，不是疏忽。

另外两处细节：signal.aborted 为真时直接 return，不再调 adapter，省掉一次必然失败的请求； clearTimer() 在 onEnd 里、也在 onError 里，成功和失败都要清，否则 Node 进程会被一个还活着的 setTimeout 拖住不退出。

最后三行处理“adapter 自己抛错”和“adapter 返回了 rejected Promise”两种形态。ret.then(null, hooks.onError) 只接失败不接成功， 因为成功路径已经通过回调走完了，不需要再传值。

04

Response：一个带终态的迷你状态机

Response.js 101 行，核心是六个私有字段。_done 管“还能不能继续推”，_sseMode / _sseBuffer 管 SSE 切块， _cancel 管中断，_errorPending 管“错误来得太早”：

packages/fetch/src/response.js:8
this.status = 0;
this.headers = {};
this.ok = false;
this._done = false; // 标记是否已经 end/error，防止重复触发
this._sseMode = false; // SSE 模式：按 \n\n 分割事件，提取 data: 字段原始字符串
this._sseBuffer = ''; // SSE 缓冲区，处理 chunk 边界
this._cancel = null; // 由 createFetch 注入，用于中断底层请求
this._errorPending = null; // 消费者还没来得及注册时就发生的错误，注册后补发

_push 的第一行是全部状态机的入口判据：

if (this._done && type !== 'error') return; —— 这就是入口判据。

为什么 error 能穿过 _done：已经 end 的请求理论上不该再出错，但真实世界里 Node 的 req 在 end 之后仍可能吐 ECONNRESET。如果这时把错误吞掉，上层会以为这是一次干净的结束。宁可重复一次错误，也不能漏报失败。

end 的处理只有一句 this._done = true，外加 SSE 模式下 flush 缓冲区。data 则完全取决于 _sseMode： 非 SSE 时原样透传字符串，把“怎么解读”留给上层；SSE 时走下一节的切块逻辑。

05

SSE 切块：为什么要留最后一段

SSE 的事件以空行分隔，但网络给你的 chunk 不按事件边界切——一个 chunk 可能是“半个事件”，也可能是“两个半事件”。所以必须有缓冲区：

packages/fetch/src/response.js:53
if (type === 'data' && this._sseMode) {
  this._sseBuffer += payload;

  // 按 \n\n 分割出完整事件，最后一段可能不完整
  const parts = this._sseBuffer.split(/\r{0,1}\n\r{0,1}\n/);
  this._sseBuffer = parts.pop();

  for (const part of parts) {
    const payload = this._extractSSEData(part);
    if (payload !== null) {
      this.emit('data', payload);
    }
  }
  return;

split(/\r{0,1}\n\r{0,1}\n/) 里那个 {0,1} 不是炫技，是等价于 \r? 的显式写法（有的服务端发 \r\n，有的只发 \n）。 parts.pop() 拿到的最后一段永远可能是“没写完的事件”，所以它被塞回 _sseBuffer 等下一块数据，不解析。 这是整套流式解析不掉字的唯一保证。

切出来之后交给 _extractSSEData 只取 data: 前缀的内容：

packages/fetch/src/response.js:96
_extractSSEData(raw) {
  const dataLines = [];
  for (const line of raw.split('\n')) {
    if (line.startsWith('data:')) {
      dataLines.push(line.replace(/^data:\s*/, '').replace(/\r$/, ''));
    }
  }
  if (dataLines.length === 0) return null;
  return dataLines.join('\n');

只认 data:，event: / id: / retry: 一律忽略，多行 data: 用 \n 拼回去（SSE 规范就是这么定义的）。 没有 data: 的块返回 null——注释行（以 : 开头的 keep-alive）就靠这个被自然丢掉，不需要额外判断。

end 时还有一次 flush：if (_sseMode && _sseBuffer.trim())。原因是有些服务端最后一条事件后面不带空行， 直接关连接；不 flush 就会丢掉最后一条。

06

错误比监听器先到，怎么办

packages/fetch/src/response.js:21
on(event, listener) {
  super.on(event, listener);
  if (event === 'error' && this._errorPending) {
    const err = this._errorPending;
    this._errorPending = null;
    // 异步补发，避免在注册栈里同步回调
    queueMicrotask(() => this.emit('error', err));
  }
  return this;

典型场景：URL 写错，adapter 在同一个 tick 内就 onError 了，而调用方还在 .then(res => res.on('error', ...)) 的路上。 直接 emit 出去，这个错误就永久丢失（native EventEmitter 在这种情况下会直接抛未捕获异常）。

所以 _push('error') 会先检查有没有监听器；没有就存进 _errorPending，等 on('error') 注册时补发。 补发用的是 queueMicrotask 而不是同步调用——如果在 on() 的栈里同步回调，监听器里再调 off() 或 cancel() 就会踩到半注册状态。

这个机制只给 error 事件开了口，data 没有。这是刻意的：数据丢了没法补救（补发等于重放，调用方会把同一段内容处理两次）， 但“请求失败了”这个事实补发一次是安全的。

07

39 行的 emitter，只做对了两件事

不用 Node 的 events、不用第三方库，是因为这个包要能在浏览器里跑，而它需要的功能只有 on / off / emit 三个。

packages/fetch/src/emitter.js:24
emit(event, ...args) {
  const list = this._events[event];
  if (!list || list.length === 0) return false;
  // 复制一份再触发，避免 off 回调过程中影响本次派发
  for (const fn of list.slice()) {
    try {
      fn.apply(null, args);
    } catch (e) {
      // 单个监听器异常不影响其它监听器，也不再冒泡成进程级异常
      console.error(e);
    }
  }
  return true;

list.slice()：先复制再遍历。否则监听器里调 off(event, other) 会让数组长度变化，后面的监听器被跳过——这类 bug 只在“取消订阅发生在派发过程中”时复现，极难查。

try/catch：单个监听器抛错不许影响其它监听器，也不许变成进程级异常。代价是错误被降级成 console.error， 在生产环境里可能没人看。这是“流式渲染不能因为一个 UI 回调挂掉而断流”的必然代价：core 那边每个 chunk 都会调一次渲染。

_events 用 Object.create(null) 而不是 {}，是为了让 toString、constructor 这类原型链上的名字也能当事件名，且不受原型污染影响。

08

两个 adapter：一个懒加载，一个读流

Node 端第一个动作不是发包，是 await import：

packages/fetch/src/adapter-node.js:7
const [{ default: http }, { default: https }, { URL }] = await Promise.all([
  import('http'),
  import('https'),
  import('url')
]);

为什么把这三个 import 放在函数里：打包器（webpack / vite / rollup）会静态扫描顶层 import，一旦看到 'http' 就会报“Node 内置模块无法在浏览器解析”，哪怕这段代码运行不到。await import() 是动态的，扫描器看不到，浏览器构建就能过。 代价是每次请求多一次已缓存的模块解析，可以忽略。

真正的请求只用 http / https 两个库里的一个，选谁由协议决定。res.setEncoding('utf8') 这一行很关键： 不设的话 chunk 是 Buffer，而 Response 的 SSE 缓冲是字符串拼接，Buffer + string 会隐式 toString()， 多字节字符（中文）被切成两半时就成乱码了。设了 setEncoding，Node 自己按字符边界解码。

packages/fetch/src/adapter-node.js:56
if (signal) {
  if (signal.aborted) {
    onError(new Error('请求已取消'));
    return;
  }
  signal.addEventListener('abort', () => {
    req.destroy(new Error('请求已取消'));

取消走 req.destroy(err)，错误从 req 的 error 事件回来——所以 adapter 不需要自己 onError，只要不吞错误就行。

浏览器端相反，原生 fetch 已经解压、已经处理重定向、已经带 signal，唯一要自己干的是读流：

packages/fetch/src/adapter-browser.js:27
const reader = res.body.getReader();
const decoder = new TextDecoder('utf-8');

// 循环读取流直到 done
// 用 async IIFE 形式启动，错误统一走 onError
(async () => {
  try {
    // eslint-disable-next-line no-constant-condition
    while (true) {
      const { value, done } = await reader.read();
      if (done) {
        onEnd();
        return;
      }
      // value 是 Uint8Array，解码为字符串
      onData(decoder.decode(value, { stream: true }));

decoder.decode(value, { stream: true }) 里的 stream: true 是同一个问题的浏览器版本：TextDecoder 默认假定每次输入都是完整文本， 加了这个选项才会把“半个 UTF-8 字符”留到下一次解码。少了它，中文流式输出会零星蹦出 �。

if (!res.body) 单独处理：204 或 HEAD 请求没有 body，getReader() 会抛 TypeError。

两端的实际差异（文档里不写会踩坑）：Node adapter 不跟随 3xx 重定向、不做 gzip 解压、不设 Accept-Encoding。 如果自家网关会 302 或强制压缩，需要在 adapter 之外处理，或者干脆在 Node 侧换掉 adapter。

09

选 adapter：一行环境判断的边界

packages/fetch/src/index.js:8
const isBrowser = typeof window !== 'undefined' && typeof window.document !== 'undefined';

const adapter = isBrowser ? browserAdapter : nodeAdapter;

const fetch = createFetch(adapter);

判据是 window 且 window.document。用两个条件而不是只看 window，是为了避开 Web Worker（有 self 没有 document）——Worker 里其实也能用原生 fetch，但会被判成 Node 分支，这是当前的已知边界。

SSR 环境：Node 里跑、没有 window，会正确落到 nodeAdapter。这也是注释里那句“SSR 环境需要 polyfill 时也能正确走 nodeAdapter”的意思： 如果你的框架在服务端注入了假的 window 但没注入 document，判断依然成立。

createFetch(adapter) 在模块加载时就执行一次，之后所有请求复用同一个闭包。adapter 是纯函数式的——不持有任何请求状态， 状态全在每次调用新建的 Response 里。这一点是这套设计能被并发安全使用的前提。
