Read 03model：请求拼装与流式解析

@auipage/model 277 行，只做一件事：把「消息数组 + 工具清单」发出去，把「返回的流」拼回 content 和 tool_calls。 它的难点全在流上——chunk 边界不落在语义边界上。

01

Model 只有三个字段

Model 不是一个 SDK 客户端，它只是一个配置容器。构造函数不校验、不给默认值：

packages/model/src/index.js:4
function Model(fields) {
    this.model = fields.model;
    this.apiKey = fields.apiKey;
    this.baseURL = fields.baseURL;

不校验是刻意的：model 名字可以是任何服务商的任何模型，baseURL 可以是自建网关、代理、本地 ollama， 校验只会把本来能用的组合挡在外面。配置错误会在第一次请求时以 HTTP 错误的形式暴露，界面上还看得见，比构造期抛错更实用。

只有一处“规整”发生在请求时，而不是构造时：this.baseURL.replace(/\/+$/, "")。 放在构造里也完全可以，但那样 model.baseURL = "..." 事后改值就会绕过规整，所以它被放在拼接 URL 的那一刻——每次请求都重新算。

apiKey 没有做任何脱敏，注释里也没有。这意味着调试时打日志很容易把它带出去；如果你在二次封装里打印 model， 要自己 Object.assign({}, model, { apiKey: "***" })。

02

completions 的状态全在一个闭包里

整个请求是 new Promise 包起来的，所有中间变量都在闭包里，不挂到任何对象上：

packages/model/src/completions.js:39
const state = { content: "", tool_calls: [] };
const callbacks = { logback, thinkback };

let buffer = "";
let httpError = null;
let streamError = null;
let settled = false;

const finish = (fn, value) => {
    if (settled) return;
    settled = true;
    fn(value);
};
const fail = value => finish(reject, toError(value, "模型请求失败"));

五个变量各有分工：state 是输出累加器（content 与 tool_calls 最后原样返回给 agent）， buffer 只在非流式下用（把整段响应攒起来一次性解析），httpError / streamError 记录“已经出过错”， settled 保证 Promise 只结束一次。

为什么 state 要跨 chunk 存活：流式下每个 chunk 只带来一小段增量，content 必须自己累加； 而 tool_calls 的第 1 片只给 id 和 index，参数是后面若干片陆续拼进来的，所以必须有一个能跨 chunk 记住槽位的对象。 这个对象里还会被塞进 _toolSlots、thinkBuf、inThink 三个“内部字段”——它们不属于对外契约，只是没有别的地方可放。

callbacks 只包了 logback / thinkback 两个回调。它们一直往下传到 handleChoices，沿途不被替换、不被判断， 所以 写 if (logback) logback(x) 这种卫语句的地方全部在 handleChoices 里，这里不必重复判断。

03

settled：为什么 Promise 必须自己看门

一个流式请求有五条可能通向失败：HTTP 4xx、parseString 抛错、handleChoices 抛错、res 的 error 事件、fetch 自身的 reject。 它们可能在同一毫秒内先后触发（比如 4xx 的同时连接被关），Promise 虽然会忽略第二次 reject，但代码会继续往下跑， 于是 flushThinkBuffer 会在已经 reject 之后再调一次 thinkback——界面上就会看到内容“回魂”。

所以有一个统一的出口：

const finish = (fn, value) => { if (settled) return; settled = true; fn(value); }

所有成功路径都走 finish(resolve, ...)，所有失败路径都走 fail(...)（内部就是 finish(reject, toError(...))）。 settled 在调用 fn 之前就置位，这不是顺序洁癖：如果先 fn() 再置位，而 resolve 触发的 then 回调里又同步调用了什么， 重入时就还会看到 settled === false。

toError 把任意形态（Error、{message}、字符串、null）收敛成 Error。 必要性来自 parseString 的 throw item.error：模型返回的 error 字段经常是普通对象或字符串，不是 Error 实例。 上层若用 catch (e) e.message 就会拿到 undefined。

04

请求体：工具传的是 description，不是 execute

packages/model/src/completions.js:56
fetch({
    url: `${this.baseURL.replace(/\/+$/, "")}/chat/completions`,
    method: "POST",
    headers: {
        "Authorization": `Bearer ${this.apiKey}`,
        "Content-Type": "application/json",
    },
    body: JSON.stringify({
        model: this.model,
        messages: params.messages,
        tools: params.tools ? params.tools.map(tool => tool.description) : [],
        stream: params.stream,
    }),
    timeout: params.timeout,
    signal: params.signal

tools: params.tools.map(tool => tool.description) 这一行是 model 与 agent 之间唯一的契约点。CreateTool 产出的对象是 { description, execute }，而 OpenAI 协议只认 { type: 'function', function: {...} }。所以这里做了一次降维： 只把 description 发出去，execute 留在进程内。函数永远不出本地，这也是这套框架敢让前端工具直接跑在页面里的原因。

tools 缺省传 [] 而不是省略字段。有些服务商（尤其兼容 OpenAI 的第三方网关）对缺失 tools 和空数组的处理不一致， 空数组是最安全的形状。

stream: params.stream 一路透传，没有做布尔归一化。传 undefined 时字段会被 JSON.stringify 直接丢掉， 服务端按默认（非流式）处理——这依赖服务端行为，属于已知的隐式约定。

timeout 和 signal 只是原样交给 fetch，model 包自己不实现超时和取消。上一页讲的那套 abortWith 就是这里的下游。

05

流式和非流式，最后都进同一个 handleChoices

两种模式的差别只有“什么时候解析、解析什么形状”，之后完全合流：

packages/model/src/completions.js:82
res.on("data", chunk => {
    if (settled) return;
    if (!params.stream) {
        buffer += chunk;
        return;
    }
    let parsed;
    try {
        parsed = parseString(chunk.toString());
    } catch (e) {
        streamError = e;
        fail(e);

流式：每个 chunk 立刻 parseString，可能一次解析出多条事件（一个 chunk 里塞了两个 data:）， 所以结果被 Array.isArray(parsed) ? parsed : [parsed] 归一，再逐条把 item.choices 交给 handleChoices。

非流式：data 时只做 buffer += chunk，什么都不解析。等到 end 事件，才把整段 buffer 解析成 { choices: [{ message }] } 的形状，然后手工包成 [{ delta: choices[0].message }] 喂给同一个 handleChoices。

这是全文件最值得学的一处设计：message 与 delta 的字段名其实不同（tool_calls 一个带 index 一个不带）， 但 handleChoices 只读 delta.content / delta.reasoning / delta.tool_calls，两种形状在这些字段上恰好同构。 于是两条路径共用一套累加逻辑，不需要写第二份解析代码。代价是：非流式的 tool_calls 没有 index， 归并时要走“没有 index 就追加到最后一个槽位”的兜底分支（下一节讲）。

校验只做一处：非流式在 end 里显式检查 choices[0].message 存在，否则抛“模型响应缺少 choices[0].message”。 流式不检查，因为流式的“空响应”是合法的（模型可能只回了 tool_calls）。

注意 end 里的判定顺序：先 streamError、再 httpError。流式下如果已经解析失败，报解析错误比报 HTTP 错误更有定位价值—— 毕竟 HTTP 已经通了，问题在格式。

06

parseString 的输入契约：七种形状都要认

这个函数不知道自己在解析哪家服务商，只知道“拿到的可能是这几种东西”。它按“先剥结束标记，再试单条，再试多事件，最后试 NDJSON”的顺序试：

packages/model/src/parseString.js:38
text = text.replace(/data:\s*\[DONE\]$/, "").trim();
if (text === "" || text === "[DONE]") return [];

data: [DONE] 的处理有个细节：它先 replace(/data:\s*\[DONE\]$/,"") 再 .trim()。 因为结束标记经常紧跟在最后一条事件后面（...}\n\ndata: [DONE]），单独判断会漏掉；剥掉之后剩下的内容继续按正常事件解析， 所以一段文本里“最后一条事件 + [DONE]”能一次拿到两条结果。

空串和 [DONE] 返回 []，而不是 null：调用方统一按“数组”处理，省掉一次类型判断。

packages/model/src/parseString.js:48
const parts = text.split(/\r?\n\r?\ndata: /);
if (parts.length > 1) return checkError(parts.map(part => parseOne(part, text)));

多条事件的切分点写死为 /\r?\n\r?\ndata: ——带空行、带 data: 空格。这是脆弱的： 如果服务端发 data: 后面没有空格，或事件之间用 \r\n\r\n 且无空格，这个分支就切不开，会落到最后的 SyntaxError。 现实里 OpenAI 兼容服务都用这个格式，所以够用；但它不是通用 SSE 解析器，这一点必须知道。

每段都经过 parseOne → stripDataPrefix → JSON.parse，失败时抛的 SyntaxError 会带上 原文前 120 字符。 这是排障最有用的一条信息：模型网关返回 HTML 错误页时，你能立刻从报错里看出来。

最后一道 checkError 是“错误体识别”：只要是 {"error": ...} 形状，无论单条还是数组里某一条，都直接 throw， 交给 completions 的 toError 收敛。这样错误判定只在一处，不会散落在各分支。

07

tool_calls 归并：index 与 id 两条线索

流式工具调用是分段下发的：第 1 片给 index: 0 + id + function.name，后面若干片只给 index: 0 + function.arguments 的碎片。要拼成一个完整的调用，必须能把碎片认出是同一个调用：

packages/model/src/streamHandler.js:17
function mergeToolCall(state, toolCall) {
    if (!state._toolSlots) state._toolSlots = new Map();

    const calls = state.tool_calls;
    const index = typeof toolCall.index === "number" ? toolCall.index : null;
    const hasId = typeof toolCall.id === "string" && toolCall.id !== "";

    // 带 id 视为新调用；同 id 重复下发时复用已有槽位
    if (hasId) {
        const exist = calls.find(call => call.id === toolCall.id);
        if (exist) {
            appendArguments(exist, toolCall);
            return;
        }
        const slot = normalizeCall(toolCall);
        calls.push(slot);
        if (index !== null) state._toolSlots.set(index, slot);
        return;
    }

    let slot = index !== null ? state._toolSlots.get(index) : null;
    if (!slot && calls.length) slot = calls[calls.length - 1];

    // 首片就没有 id：建占位槽位，后续分片补齐参数
    if (!slot) {
        slot = normalizeCall(toolCall);
        calls.push(slot);
        if (index !== null) state._toolSlots.set(index, slot);
        return;
    }

    appendArguments(slot, toolCall);

判定顺序是三层兜底：

1. 有 id → 当作新调用，先按 id 查重：已存在就只追加参数（同一条 id 被重复下发的情况）， 不存在就 normalizeCall 建槽并登记到 _toolSlots[index]。 normalizeCall 只保证 function.arguments 是字符串——有的服务商首个分片给 arguments: ""， 有的干脆不给，后续要 +=，类型不对就会拼成 "undefined{...}"。

2. 无 id 有 index → 从 _toolSlots 里取回槽位。这就是 Map 存在的理由： index 是唯一的稳定标识，calls 数组里的位置会因并发调用顺序变化。

3. 两个都没有 → 追加到 calls[calls.length - 1]，也就是“认为它是上一条的续片”。 这条兜底是给非流式路径准备的：那里 tool_calls 是完整对象、没有 index，一次进来就是一个完整调用。

appendArguments 只做两件事：fn.name 若槽位还没有就补上（有的模型把 name 放在后面的分片里）， arguments 字符串直接 +=。它不做 JSON 解析——解析留到 callFuns 执行工具时，因为拼接中途的字符串一定不是合法 JSON。

08

think 标签：把“半个标签”留在缓冲区

有些模型（如 MiniMax 系列）把思考过程写成 <think>...</think> 混在 content 里。剥离它的难点不是找标签， 而是 chunk 可能正好切在标签中间：你收到 "<thi"，下一块才是 "nk>..."。这时不能把 <thi 当正文发出去。

packages/model/src/reasoning.js:20
function partialTagLength(text, tag) {
    const max = Math.min(tag.length - 1, text.length);
    for (let len = max; len > 0; len--) {
        if (text.endsWith(tag.slice(0, len))) return len;
    }
    return 0;

partialTagLength 从“最长可能前缀”往短里试，返回文本尾部与标签前缀重合的长度。 比如 text = "abc<thi"、tag = "</think>"，它会返回 4，于是最后 4 个字符被扣下来存进 state.thinkBuf，等下一块到了再拼回去判断。注意 max = tag.length - 1：整标签不会是“前缀”，排除掉它才能避免死循环。

extractThink 用两个状态字段跨 chunk 记录：inThink（现在是否在思考块里）与 thinkBuf（被扣下的半截）。 四种情况的处理各不相同：

在思考块内找到 </think> → 前面的都归 thinking，退出思考态，剩余内容递归（可能后面又有一个完整的 <think> 块）。

在思考块内没找到 → 扣下可能的标签尾巴，其余全归 thinking，content 给空串。

不在思考态 → 找 <think>；找不到就只扣标签尾巴，其余都是正文。

有 <think> 没 </think> → 进入思考态，<think> 之前的是正文，之后的都算思考。

流结束时，thinkBuf 里可能还剩一段永远等不到配对的文本（服务端直接断了）。flushThinkBuffer 按当前所处模式归属输出： 在思考态就归 thinkback，否则归 logback 并累加进 state.content。不 flush 就会丢字， 而且丢的通常是最后几个字，用户会觉得“模型话说一半停了”。
